## 시나리오별 상세 확인 내용

- **S-1/S-2/S-3**: 초기 화면 → 강사 진입 → 수강생("홍길동"/s01) 진입까지 정상. 수강생 입장 즉시 강사 화면에만 접속자 목록·1:1 대상 라디오가 실시간 반영됨(PRD 6항: 수강생 화면엔 입퇴장 시스템 메시지 미노출 — 확인됨, 최신 UI는 토스트 알림 방식으로 구현되어 있고 수강생에게는 애초에 전송되지 않음).
- **S-4**: "s01" 중복 식별자 입력 시 화면 전환 없이 인라인 에러("이미 사용 중인 식별자입니다. 다시 입력해주세요.") 노출, "s02"로 재입력 후 정상 재시도 성공.
- **S-5/S-6**: 강사가 지정한 폴더(`e2e/share-fixture`, 하위 `chapter1/index.html` + `readme.md`)가 `share_updated` 브로드캐스트로 두 수강생 화면에 즉시 반영. 다운로드 정상. 경로 탈출(`../../etc/passwd`) 시도는 서버가 `400 INVALID_PATH`로 차단 확인(fetch로 직접 검증).
- **S-7/S-8/S-8-A**: 강사→전체, 강사→특정 학생(홍길동), 학생→강사만 세 케이스 모두 대상 격리가 정확함 — 관련 없는 제3자(김철수/홍길동)에게 노출되지 않음을 각 탭에서 교차 확인.
- **S-9/S-10**: 포커스가 입력창이 아닌 상태에서도 `Ctrl+V` 이미지 붙여넣기, 입력창 밖 영역에 파일 드롭 모두 정상 수신·전송·썸네일/링크 렌더링. 저장 파일명이 "원본이름.해시.확장자"(`app.5ec96390.js`) 형태로 유지됨(PRD 요구사항 일치).
- **S-11/S-16**: 우클릭 시 타인의 메시지는 "복사하기"만, 본인 메시지는 "복사하기"+"삭제하기"(빨간 글자) 노출. 삭제 시 전체 접속자 화면에서 즉시 사라짐. **권한 없는 삭제 시도**(다른 사용자 identifier로 타인 메시지 delete 전송)는 서버가 조용히 무시하고 메시지가 그대로 남아있음을 REST 조회로 재확인(S-16.5 정확히 일치).
- **S-12/S-13**: 관리자 조회에는 시스템(join) 이벤트와 전체 로그가 포함되고, 학생(김철수/s02) 조회에는 시스템 메시지와 타 학생 대상 1:1(강사→s01)이 제외됨을 `GET /api/messages` 응답으로 검증. `GET /api/messages/export`도 동일 필터가 적용된 Markdown으로 응답(`Content-Disposition: attachment; filename="2026-08-11.md"`).
- **S-14**: 학생 탭 종료 시 서버가 세션 제거 후 강사 화면의 접속자 수/목록이 실시간 갱신됨(재검증 시 정상 확인, 최초 시도에서는 아래 "발견된 이슈"로 인해 갱신되지 않는 것처럼 보였음).
- **S-15**: 서버 프로세스 재기동(파일 워처로 트리거, `keep-alive.js`와 동일한 JWT 시크릿 재생성 효과) 후 기존 토큰을 쓰던 열린 탭이 WebSocket close(4401)를 수신하고 자동으로 S1 로그인 화면으로 리다이렉트됨을 확인.
- **S-17**: 이미지 썸네일 클릭 → 라이트박스 오버레이(원본 이미지 + ✕ 닫기) 노출, ✕ 클릭으로 정상 닫힘.
- **S-18**: 11MB 더미 파일 드롭 시 클라이언트가 전송 자체를 막고 "파일이 너무 큽니다 (최대 10MB, 11.0MB)" 인라인 에러 표시. 클라이언트 우회를 가정해 WebSocket으로 11MB base64 페이로드를 직접 전송한 결과, 서버도 재검증 후 `error`(`FILE_TOO_LARGE`)로 거부하고 저장/브로드캐스트하지 않음을 확인(PRD 보안 요구사항 일치).
- **S-19**: 강사 화면 사이드바 상단에 LAN 주소 2건(`http://10.30.0.37:5057`, `http://172.27.160.1:5057`)이 자동 노출됨.

## 발견된 이슈

### [중] 동일 JWT로 다중 WebSocket 연결 시 세션 맵이 덮어써져 "좀비 연결" 발생

**증상:** 같은 로그인 토큰(JWT)으로 두 번째 WebSocket 연결을 열었다가 닫으면, 먼저 연결되어 있던 정상 탭이 서버로부터 더 이상 어떤 브로드캐스트도 받지 못하는 상태(TCP 연결 자체는 살아있으나 메시지/유저목록 갱신 없음)가 된다.

**원인 추정:** `server/src/state.js`의 `addSession(session)`이 `sessions.set(session.identifier, session)`으로 동작하는데, 강사(admin) 역할은 `isIdentifierTaken` 충돌 검사 대상이 아니라서 동일 identifier로 여러 WebSocket을 열 수 있다. 두 번째 연결이 맵 엔트리를 덮어쓴 뒤 그 연결만 닫히면 `removeSession(identifier)`가 원래(첫 번째) 연결의 세션까지 맵에서 지워버려, 첫 번째 소켓은 연결 유지 상태로 남지만 `broadcastToAll`/`broadcastToAdmins`의 순회 대상에서는 빠지게 된다.

**재현 경로:** 실제 사용자 플로우(브라우저 탭 하나만 사용)에서는 거의 발생하지 않으나, 브라우저 개발자 콘솔이나 확장 프로그램 등에서 같은 토큰으로 별도 WebSocket을 열었다 닫는 경우, 또는 네트워크 문제로 클라이언트가 재연결을 시도하며 이전 소켓이 완전히 닫히기 전에 새 소켓을 여는 레이스 컨디션에서 실사용자에게도 나타날 수 있다.

**제안:** identifier당 세션은 항상 1개만 유효하도록, 새 연결 등록 시 동일 identifier의 기존 세션이 있으면 해당 소켓을 명시적으로 `close()`한 뒤 교체하거나, 세션 객체 자체(소켓 인스턴스)를 키로 별도 관리해 "가장 최근 연결"만이 아니라 "현재 이 소켓이 맵의 소유자인지"를 확인 후 삭제하도록 `removeSession`을 `removeSession(identifier, ws)` 형태로 바꿔 자기 자신의 세션일 때만 지우는 방식을 권장.

**영향도:** 강의 중 실사용에서는 재현 빈도가 낮을 것으로 예상되나(정상 플로우에서 동일 토큰 다중 연결이 흔치 않음), 한번 발생하면 사용자가 "메시지가 안 와요"라며 새로고침해야 알아채는 조용한 실패(silent failure)라 디버깅이 어려움 — 우선순위는 중간 정도로 판단.

## 특이사항 / 참고

- 최신 커밋(`사설 인증서 기반 HTTPS 지원 + 입퇴장 알림 토스트로 변경`)에 따라 입퇴장 시스템 메시지가 대화창에 누적되지 않고 3초짜리 토스트로만 표시되도록 UI가 바뀌어 있음 — 시나리오 문서(S-3, S-14)의 "시스템 메시지 브로드캐스트" 자체는 여전히 유효(서버 로그·MD 내보내기에는 포함), 화면 표현 방식만 문서 작성 시점과 달라진 것으로 문서 업데이트를 권장.
- HTTPS/사설 인증서(S-1 관련, README 절차)는 이번 E2E 대상에서 제외(자동화 브라우저의 자체서명 인증서 신뢰 설정이 추가로 필요해 범위 밖으로 판단). 인증서 유무에 따른 HTTP/HTTPS 분기 로직(`server/src/index.js`)만 코드 리뷰로 확인.
