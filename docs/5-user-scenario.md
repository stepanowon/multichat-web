# MultiChat Web 사용자 시나리오

**버전:** 1.1
**작성일:** 2026-08-09
**최종 수정:** 2026-11-17 (설문 S-22~S-27, HTTPS S-28 추가, 입퇴장 토스트·강사 삭제 권한·첨부 경로 반영)
**관련 문서:** [1-prd.md](./1-prd.md), [2-stack.md](./2-stack.md), [3-wireframe.md](./3-wireframe.md), [4-api.md](./4-api.md)

## S-1. 서버 구동 & 패스워드 준비

1. 강사(또는 운영자)가 서버 실행 전 환경변수 `ADMIN_PASSWORD`, `STUDENT_PASSWORD`를 지정(또는 `server/.env`)하고 `server`에서 `npm start` 실행. 둘 중 하나라도 없으면 서버가 즉시 종료.
2. `npm start`는 `keep-alive.js`로 서버를 띄우고, 저장소에 커밋된 프론트 빌드(`server/static`)를 그대로 서빙(개발용 `npm run dev`는 `predev` 훅이 먼저 프론트를 빌드). 두 패스워드는 메모리에 로드, 이후 모든 로그인 요청을 이 값과 직접 비교(파일/DB 저장 없음).
3. 브라우저로 접속하면 앱 내 초기 설정 화면 없이 바로 S1(진입 화면)이 뜸.

## S-2. 강사 로그인 & 입장

1. S1에서 강사 카드에 관리자 패스워드 입력, "입장하기".
2. `POST /api/login/admin` → 성공 시 JWT 발급, `sessionStorage`에 저장.
3. WebSocket `ws://.../ws?token=<JWT>` 연결 → 서버가 이 연결을 세션에 등록, `welcome`과 현재 `user_list` 수신.
4. S2(관리자 채팅 화면) 진입. 좌측 접속자 목록에는 이미 접속해 있는 수강생이 바로 표시(없으면 빈 목록 — 강사 본인은 목록에 없음).
5. 강사가 같은 패스워드로 탭을 하나 더 열어도 각 탭이 독립적으로 모든 메시지·알림을 받는다.

## S-3. 수강생 로그인 & 입장(정상)

1. S1에서 수강생 카드에 닉네임 "홍길동", 고유식별자 "s01", 공통 패스워드 입력, "입장하기".
2. `POST /api/login/student` → 서버가 패스워드 검증 + 식별자 중복 없음 확인 → JWT 발급.
3. WebSocket 연결 → 서버가 세션에 등록 → **강사 화면에만** `system`(join) + `user_list` 갱신 브로드캐스트. 강사 화면엔 "홍길동님이 입장했습니다" 토스트가 3초간 떴다 사라지고 접속자 목록에 추가됨. 홍길동 화면엔 아무 시스템 메시지도 안 뜸(PRD 6항).
4. S3(수강생 채팅 화면) 진입. 좌측 패널엔 공유 파일 목록(`GET /api/share/files`) 표시.

## S-4. 수강생 로그인 — 고유식별자 충돌

1. 다른 수강생이 이미 "s01"로 접속 중인 상태에서 새 사용자가 동일 식별자 "s01"로 입력, "입장하기".
2. `POST /api/login/student` → 서버 응답 409 `IDENTIFIER_TAKEN`.
3. S1 화면 전환 없이 식별자 입력창 아래 인라인 에러 표시, 포커스 이동 → 사용자가 "s01-2" 등으로 재입력 후 재시도.

## S-4-A. 수강생 로그인 — 예약된 이름("강사") 사용 시도

1. 사용자가 닉네임 또는 고유식별자에 "강사"를 정확히 입력(앞뒤 공백 포함 가능), "입장하기".
2. `POST /api/login/student` → 서버가 trim 후 완전 일치 여부 확인 → 400 `RESERVED_NAME`.
3. S1 화면 전환 없이 인라인 에러 표시, 사용자가 다른 이름으로 재시도. ("보조강사"처럼 "강사"를 포함하되 완전히 같지 않은 이름은 정상 통과.)
4. 표시 문구: "'강사'는 닉네임이나 고유식별자로 사용할 수 없습니다." 빈 칸(공백만 입력 포함)은 400 `MISSING_FIELDS` → "닉네임, 고유식별자, 패스워드를 모두 입력해주세요."

## S-5. 강사 — 공유 디렉토리 지정

1. 강사가 S2에서 "공유 폴더 지정" 클릭 → S4 모달.
2. 서버 경로 `/srv/course/day1` 입력, "지정하기".
3. `POST /api/share/dir` → 경로 유효성 검증(존재하는 디렉토리인지) 통과 시 서버가 지정 경로 기억(메모리 — 서버 재기동 시 다시 지정). 실패하면 모달에 "존재하지 않는 디렉토리입니다." 표시.
4. 서버가 전체 접속자에 WebSocket `share_updated` 브로드캐스트 → 모든 수강생 화면이 `GET /api/share/files` 재조회, 새로고침 없이 좌측 파일 목록 갱신.

## S-6. 수강생 — 파일 다운로드(하위 폴더 포함)

1. 수강생이 S3 좌측 파일 트리에서 `chapter1/index.html` 항목 확인(하위 폴더도 트리로 펼쳐짐).
2. 다운로드 클릭 → `GET /api/share/download?path=chapter1/index.html`.
3. 서버가 지정 루트 하위 경로인지 검증 후 스트리밍 응답 → 브라우저 다운로드.
4. (탈출 시도) `path=../../etc/passwd`, 절대경로, 폴더 경로 같은 요청은 서버가 400 `INVALID_PATH`로 거부. 토큰 없이 요청하면 401.

## S-7. 강사 → 전체 브로드캐스트 메시지

1. 강사가 S2 "받는 사람"에서 "전체" 선택, 메시지 입력 후 전송.
2. WebSocket `message`(msgType:text, to:"all") 전송 → 서버가 날짜별 `.jsonl`에 append 저장 후 접속 중인 전원(강사 포함)에게 `message` 브로드캐스트.
3. 모든 수강생 화면 대화창에 즉시 표시.

## S-8. 강사 → 특정 수강생 1:1 메시지

1. 강사가 "받는 사람" 드롭다운에서 "홍길동" 선택 후 메시지 전송(to:"s01").
2. 서버가 받는 사람 닉네임(`toNickname:"홍길동"`)과 함께 저장 후 강사 본인 + identifier "s01" 소켓에만 `message` 전달.
3. 홍길동 화면엔 발신 정보 옆에 "(나에게)"로 표시. 다른 수강생 화면엔 노출 안 됨.
4. 홍길동이 퇴장하거나 강제 종료되어 목록에서 사라지면 강사의 "받는 사람"이 자동으로 "전체"로 돌아감.

## S-8-A. 수강생 → 전체 사용자 / 강사 선택 전송

1. 수강생이 S3 좌측 "받는 사람"에서 "전체 사용자"(기본값) 또는 "강사" 선택.
2. "전체 사용자" 선택 시 WebSocket `message`(to:"all") 전송 → 강사 포함 접속 중인 모두에게 브로드캐스트, 다른 수강생 화면에도 표시.
3. "강사" 선택 시 WebSocket `message`(to:"admin") 전송 → 강사와 본인 화면에만 표시, 다른 수강생은 못 봄.
4. 수강생이 `to`에 다른 학생 identifier를 직접 넣어 보내도 서버가 "admin"으로 강제 — 학생 간 1:1은 불가.

## S-9. 클립보드 이미지 붙여넣기 전송

1. 사용자가 스크린샷을 클립보드에 복사한 뒤 채팅 화면 아무 곳에서 `Ctrl+V`(입력창에 포커스가 없어도 됨).
2. 프론트가 `ClipboardEvent.clipboardData.items`에서 이미지 감지 → 크기 확인 후 base64 인코딩해 WebSocket `message`(msgType:image) 전송.
3. 서버가 `data/messages/images/<date>/image.<해시8자리>.png`로 저장, 로그엔 경로만 기록 → 수신자에게 이미지 메시지 전송, 대화창에 썸네일 표시(`/attachments/images/...`).

## S-10. 파일 드래그앤드롭 전송

1. 사용자가 탐색기에서 파일을 대화 영역 위로 드래그 → 대화 영역 전체에 점선 하이라이트 표시(대화 영역 밖에 떨어뜨려도 브라우저가 파일을 새 탭으로 열지 않음).
2. 드롭 → WebSocket `message`(msgType:file, fileData, fileName) 전송. 이미지 파일이면 msgType:image.
3. 서버가 `원본이름.해시8자리.확장자`로 저장(파일명의 경로 구분자·예약 문자는 `_`로 치환), 이후 흐름은 S-9와 동일. 대화창엔 파일명 + 다운로드 링크로 표시 — 클릭하면 항상 다운로드되고 브라우저에서 열리지 않음.
4. 입력창 왼쪽 `＋` 버튼으로 파일을 골라도 같은 처리(크기 검사·전송)를 거친다.

## S-11. 메시지 우클릭 복사

1. 사용자가 대화창의 특정 텍스트 메시지 위에서 마우스 우클릭.
2. 브라우저 기본 컨텍스트 메뉴 대신 커스텀 메뉴("복사하기") 표시.
3. 클릭 시 원문을 클립보드에 복사 → 메뉴 닫힘. 바깥 클릭해도 메뉴 닫힘. (`http://<LAN IP>` 접속처럼 `navigator.clipboard`가 없는 환경에선 `execCommand("copy")` 폴백으로 복사)

## S-12. 날짜별 대화 조회

1. 사용자가 상단바 날짜 드롭다운 클릭 → `GET /api/messages/dates` 결과로 채워진 목록 표시.
2. "2026-08-08" 선택 → `GET /api/messages?date=2026-08-08` 호출, 대화창을 해당 날짜 메시지로 교체.
3. 수강생 조회 시 시스템 메시지(입퇴장)와 본인 무관 1:1 메시지는 응답에서 제외된 상태로 옴.
4. 각 메시지 시각은 서버가 보관한 UTC 값을 브라우저가 접속자의 로컬 타임존으로 변환해 표시(예: UTC 01:49 → 한국 시간 10:49).
5. 날짜 구분은 한국 시간 기준 — 오전 9시 이전 메시지도 그날 날짜로 묶인다. 날짜를 빠르게 바꿔도 늦게 도착한 이전 날짜 응답이 화면을 덮어쓰지 않는다.

## S-13. 대화 Markdown 다운로드

1. 사용자가 날짜 선택 후 "MD 다운로드" 클릭.
2. `GET /api/messages/export?date=2026-08-08` → 서버가 해당 날짜 로그를 읽어 Markdown 변환(이미지는 `images/<date>/` 상대경로 링크 포함) 후 `.md` 파일로 응답.
3. 브라우저가 `2026-08-08.md` 다운로드.
4. 강사의 1:1 메시지는 `### 10:04 강사 → 홍길동`처럼 받는 사람 닉네임으로 표기(예전 로그도 같은 날 기록에서 이름을 찾아 표기). 수강생이 받은 파일엔 본인이 볼 수 있는 메시지만 들어 있고 다른 수강생의 1:1 대화나 이름은 나오지 않는다.

## S-14. 접속 종료(퇴장)

1. 수강생이 탭을 닫거나 새로고침 → WebSocket 연결 끊김 감지.
2. 서버가 그 연결의 세션을 제거 → **강사 화면에만** `system`(leave) + `user_list` 갱신 브로드캐스트(강사 화면에 "홍길동님이 퇴장했습니다" 토스트).
3. 같은 식별자로 재접속 시(S-3과 동일 플로우) 정상 재입장 가능(직전 접속자가 사라졌으므로 충돌 없음).

## S-15. 토큰 만료/서버 재기동

1. 서버가 재기동되면 JWT 서명 시크릿이 새로 생성되어 기존에 발급된 토큰이 전부 무효화됨.
2. 재기동 후 남아있던 클라이언트가 REST 요청 시 401 `INVALID_TOKEN`, WebSocket은 close(4401) 수신.
3. 클라이언트는 자동으로 S1 로그인 화면으로 리다이렉트, 사용자는 재로그인.

## S-16. 메시지 삭제 (본인 / 강사)

1. 사용자가 본인이 보낸 메시지를 우클릭 → 컨텍스트 메뉴에 "삭제하기"(빨간 글자) 표시. 강사는 수강생이 보낸 메시지에도 "삭제하기"가 표시된다(부적절한 메시지 정리용).
2. 클릭 시 WebSocket `delete`(id, date) 전송.
3. 서버가 발신자 본인 것인지(강사는 생략) 확인 후 해당 날짜 로그에서 제거(첨부파일 있으면 같이 삭제) → 전체 접속자에 `deleted`(id) 브로드캐스트.
4. 그 메시지를 화면에 갖고 있던 모든 사용자(강사·수강생 구분 없이) 화면에서 즉시 사라짐. 갖고 있지 않던 사용자는 아무 변화 없음.
5. (권한 없음) 수강생이 다른 사람이 보낸 메시지의 id로 `delete`를 보내면 서버가 조용히 무시 — 화면 변화 없음. 수강생 화면에선 남의 메시지에 "복사하기"만 표시.

## S-17. 이미지 확대보기 & 다운로드

1. 사용자가 대화창의 이미지 썸네일 클릭 → 어두운 배경의 전체화면 오버레이(라이트박스)에 원본 표시.
2. 배경 클릭 또는 우측 상단 ✕ 클릭 → 라이트박스 닫힘.
3. 이미지 썸네일 우클릭 → 컨텍스트 메뉴에 "이미지 다운로드" → 클릭 시 브라우저가 원본 파일명(예: `image.a1b2c3d4.png`)으로 다운로드.

## S-18. 10MB 초과 첨부 시도

1. 사용자가 10MB보다 큰 파일을 드래그앤드롭·클립보드 붙여넣기·`＋` 버튼으로 보내려 함.
2. 클라이언트가 전송 전에 크기 확인 → 초과 시 전송 자체를 막고 입력창 위에 "파일이 너무 큽니다 (최대 10MB, X.XMB)" 인라인 에러 표시.
3. (클라이언트 우회 시 방어) 서버도 base64 디코딩 후 실바이트 크기를 재검증 → 초과 시 `error`(`FILE_TOO_LARGE`) 응답(화면엔 alert), 저장/브로드캐스트 안 함. 15MB를 넘는 프레임은 서버가 받기 전에 연결을 끊고(close 1009), 클라이언트는 5초 후 재연결 — 서버는 영향 없음.

## S-19. 강사 — 수강생 접속 주소 확인

1. 강사가 S2 진입 시 좌측 사이드바 상단에 `GET /api/server-info` 결과로 서버 LAN 주소(예: `http://172.30.1.29:5000`, HTTPS로 떠 있으면 `https://...`) 표시. 네트워크 어댑터가 여럿이면 주소도 여러 개.
2. 복사 버튼 클릭 → 클립보드에 주소 복사(보안 컨텍스트 아니면 `execCommand` 폴백 사용) → 강사가 수강생들에게 이 주소를 안내.
3. 조회 가능한 주소가 없으면(네트워크 인터페이스 없음 등) "접속 가능한 주소를 찾지 못했습니다" 표시.

## S-20. 서버 크래시 → 자동 복구

1. 서버 프로세스가 예외로 죽음(또는 관리자가 실수로 강제 종료).
2. `keep-alive.js`가 1초 후 서버를 자동 재기동(재기동 시 JWT 시크릿이 새로 생성되어 기존 토큰은 전부 무효화 — S-15와 동일).
3. 접속해 있던 클라이언트들은 WebSocket이 끊긴 것을 감지하고 5초 후 자동 재연결 시도.
4. 서버가 이미 다시 떠 있으면 재연결 성공 → 하지만 토큰이 무효화된 상태라 서버가 close(4401) 응답 → 클라이언트가 세션을 지우고 S1(로그인 화면)으로 이동, 사용자는 재로그인.
5. 로그인 화면 진입 전 잠깐(서버가 아직 안 뜬 순간)은 재연결이 계속 실패하다가, 서버가 완전히 뜨면 다음 5초 주기 시도에서 정상 연결됨.
6. 대화 로그·첨부·설문은 파일에 저장돼 있어 재로그인하면 그대로 보인다. 공유 디렉토리 지정은 메모리라 강사가 다시 지정해야 한다.
7. 수강생 한 명이 비정상 메시지(잘못된 타입, 너무 큰 프레임 등)를 보내도 서버는 그 메시지만 무시하고 죽지 않는다 — 이 시나리오는 예기치 못한 오류에 대한 마지막 안전망이다.

## S-21. 강사 — 수강생 연결 강제 종료

1. 강사가 S2 접속자 목록에서 특정 수강생 항목의 `✕` 클릭.
2. 확인창("○○님의 연결을 강제로 종료하시겠습니까?") 표시 → 강사가 확인.
3. WebSocket `kick`(identifier) 전송 → 서버가 admin 권한 확인 후 대상 식별자의 `sessionVersion`을 올려 기존 JWT를 무효화하고, 대상 학생 소켓을 close(4403).
4. 서버가 그 연결의 세션을 제거 → 강사 화면에 `system`(leave) + `user_list` 갱신 브로드캐스트(S-14와 동일 흐름 — "○○님이 퇴장했습니다" 토스트, 받는 사람이 그 수강생이었으면 "전체"로 복귀).
5. 대상 수강생 클라이언트는 close 코드 4403을 감지 → 재연결을 시도하지 않고 `sessionStorage`를 비운 뒤 "강사에 의해 연결이 종료되었습니다." 안내 후 로그인 화면(S1)으로 이동. 같은 식별자로 다시 로그인해야 재접속 가능(기존 JWT는 `sessionVersion` 불일치로 서버가 거부하므로, sessionStorage를 비우지 않고 재사용을 시도해도 401/4401로 차단됨).
6. (경합 상황 대비) 만약 close 처리가 완료되기 직전 그 수강생이 메시지를 보내려 하면, 클라이언트가 소켓이 이미 닫힌 상태임을 감지해 전송을 실패 처리하고 즉시 로그인 화면으로 이동한다("잠시 후 재시도"로 오인하지 않도록).

## S-22. 강사 — 설문 등록

1. 강사가 S2 상단바 `설문` 버튼 클릭 → S5 설문 패널(목록) → `＋ 새 설문 만들기`.
2. 제목 입력 후 질문을 하나씩 구성: 기본 다지선다 질문 1개에 선택지를 채우고, `＋ 단답형 질문`/`＋ 다지선다 질문`으로 추가. 질문마다 유형 변경, ▲▼로 순서 이동, ✕로 삭제. 다지선다는 `＋ 선택지 추가`와 "복수 선택 허용" 체크.
3. `설문 등록` → `POST /api/surveys`. 서버가 검증(질문 1~50개, 선택지 2~20개, 빈 내용 금지 등) 실패 시 400 `INVALID_SURVEY` + "2번 질문 내용을 입력하세요(최대 500자)." 같은 문구를 폼 하단에 표시, 입력은 그대로 유지.
4. 성공 시 `data/surveys.json`에 저장, 전체 접속자에 WS `survey_updated` → 상세 화면으로 이동. 수강생 화면의 `설문` 버튼에 미응답 배지가 즉시 늘어남.
5. 수강생이 `POST /api/surveys`를 직접 호출하면 403 `FORBIDDEN`.

## S-23. 수강생 — 설문 응답·수정

1. 수강생이 배지가 붙은 `설문` 버튼 클릭 → 목록에서 `미응답` 태그가 붙은 설문 선택 → 상세(`GET /api/surveys/:id`).
2. 다지선다는 라디오(복수 선택이면 체크박스), 단답형은 텍스트 입력 후 `제출` → `POST /api/surveys/:id/responses`.
3. 빠진 질문이 있으면 400 `INVALID_ANSWERS`, "1번 질문의 답을 선택하세요." 같은 문구 표시.
4. 성공 시 "응답을 제출했습니다." → 목록 태그가 `응답함`, 배지 숫자 감소. 결과 영역에 본인 선택지에 `내 선택` 태그.
5. 마감 전에는 같은 화면에서 답을 바꿔 `응답 수정` 가능(1인 1응답, 덮어씀).

## S-24. 설문 결과 실시간 조회

1. 누군가 응답하면 서버가 `survey_updated` 브로드캐스트 → 목록과 열려 있는 상세가 새로고침 없이 재조회돼 응답 수·막대가 갱신.
2. 수강생 화면 결과는 "결과 (익명)" — 선택지별 인원·비율과 단답 내용만, 이름 없음.
3. 강사 화면 결과는 선택지별 응답자 이름과 단답 작성자 이름까지 표시.

## S-25. 강사 — 설문 마감·재개·삭제

1. 강사가 상세에서 `마감하기` → `PATCH /api/surveys/:id {closed:true}` → 모든 화면에서 상태가 `마감`으로 바뀌고 수강생 응답 폼이 사라짐(응답 안 한 수강생은 "마감된 설문이라 응답할 수 없습니다."). 마감 후 응답 요청은 409 `SURVEY_CLOSED`.
2. `다시 열기` → `{closed:false}`로 재개.
3. `삭제` → 확인창("○○ 설문을 삭제하시겠습니까? 응답도 모두 삭제됩니다.") → `DELETE /api/surveys/:id` → 강사 화면은 목록으로 돌아가고, 모든 화면의 목록에서 사라짐. 그 설문을 열어 두고 있던 다른 화면엔 "삭제된 설문입니다."와 `목록으로` 버튼 표시.

## S-26. 설문 결과 Markdown 다운로드

1. 강사 또는 수강생이 설문 상세에서 `결과 MD 다운로드` 클릭 → `GET /api/surveys/:id/export?token=...`.
2. 브라우저가 `설문결과_<제목>.md`로 저장(제목의 파일명 금지 문자는 `_`로 치환).
3. 내용: 상태·등록 시각·응답 수·내보낸 시각, 다지선다는 표(응답 수·비율), 단답형은 목록. 강사가 받은 파일엔 응답자 이름이 들어가고, 수강생이 받은 파일은 익명 집계만.

## S-27. 서버 재기동과 설문

1. 설문과 응답은 `data/surveys.json`에 저장돼 서버가 재기동돼도 유지된다(S-20 후 재로그인하면 그대로 보임).
2. 파일은 임시파일에 쓴 뒤 교체하므로 쓰는 도중 서버가 죽어도 깨지지 않는다. 만약 파일이 깨져 있으면 `surveys.json.corrupt-<시각>`으로 보존하고 빈 목록으로 시작한다.

## S-28. HTTPS로 운영

1. 강사가 강의 시작 전 그날의 IP로 자체서명 인증서를 발급해 저장소 루트 `certs/key.pem`, `certs/cert.pem`에 둔다(명령은 README 참고).
2. `npm start` → 콘솔에 `https://localhost:<PORT>`로 뜨면 적용된 것. 인증서가 없으면 평소처럼 HTTP로 뜬다.
3. 강사 화면의 수강생 접속 주소도 `https://<IP>:<PORT>`로 바뀐다. 수강생은 접속 후 브라우저의 인증서 경고를 수동으로 수락해야 한다.
4. 실시간 연결은 자동으로 `wss://`를 쓴다. 이 모드에서는 HTTP 접속은 받지 않는다.
